# 关键机制与契约决策

本文件承接 05-architecture-design.md 的形态与边界决策，处理会长期锁定行为的机制层选择：身份与授权、异步与可靠副作用、事务并发与缓存、API/事件契约、配置秘密与可观测性。

只在 05 的机制清单把某一项标为“现在必须有”或“由风险触发”时加载本文件。全部标为“明确不需要”的项目可以跳过，并在 05 的 ADR 中记录跳过理由。

## 入口

- 05-architecture-design.md 已确定系统形态、模块边界和数据所有权；
- 04-constraints-quality-risks.md 的 Q-ID 和风险登记可追踪；
- 已知哪些机制由验收场景（A-ID）或风险触发，而不是凭“以后可能需要”引入。

## 关键机制决策

每一项标记“现在必须有 / 明确不需要 / 由风险触发”，并写出理由。

### 身份、授权和租户

- 认证（Authentication）回答“你是谁”：session、短期 token、OAuth/OIDC 或服务凭据；
- 授权（Authorization）回答“你能对哪个资源做什么”：RBAC、ABAC、资源所有权、租户边界；
- 默认拒绝；在真实入口和每个敏感用例上执行授权，不能只在前端隐藏按钮；
- 服务间调用使用短期身份、最小权限和可轮换凭据；
- 需要时记录登录、授权变化、敏感读取和管理操作的审计；
- 多租户项目明确 tenant_id、跨租户查询禁止、管理员例外和索引策略；
- 未登录、过期、无权限、资源不存在的响应语义要稳定且不泄露敏感信息。

### 异步任务与可靠副作用

只有存在长耗时、削峰、重试、定时、批处理或用户不必等待的工作时才引入异步。为每个任务定义：

- 输入和版本、状态机、幂等键和结果查询；
- 投递语义（至少一次/至多一次）以及重复执行的效果；
- 超时、退避重试、最大尝试次数、顺序和并发限制；
- 死信队列、人工重放、告警和保留期；
- 数据库事务与消息之间的一致性（必要时 outbox/inbox）；
- 不可重试错误、补偿动作和部分成功的用户可见状态。

重试不能修复非幂等副作用；支付、发信、扣库存等操作要先定义幂等和补偿。

### 事务、并发和缓存

- 明确每个用例的事务边界和隔离级别；
- 乐观锁、唯一约束或分布式锁解决哪类冲突，锁的持有时间和失败语义是什么；
- 缓存只保存可重建或有明确失效策略的数据，记录一致性容忍度、TTL、穿透/击穿和主动失效；
- 限流按用户、租户、IP、令牌或资源定义，超过限额的状态和重试提示稳定；
- 文件上传定义大小/类型校验、病毒扫描、对象所有权、访问 URL、删除和生命周期；
- 搜索/通知/feature flag 只在有验收场景或风险驱动时加入，不为“以后可能需要”预置平台。

## API 与事件契约

### 风格选择

- REST：资源和标准 HTTP 语义清晰、公开客户端多时优先；
- RPC：内部命令/查询、强类型和低延迟调用，或业务动作比资源更自然时使用；
- GraphQL：客户端查询形状差异大且有成熟治理时使用；需防止深查询、授权遗漏和缓存复杂度；
- 事件：消费者不必同步等待、需要解耦或审计时使用；事件不是隐藏的远程调用。

一个项目可以混用，但每条边界要记录风格、责任和兼容策略。

### 统一响应和错误

公共 API 至少统一 request_id、版本、分页、时间/金额格式和错误信封。例如：

~~~json
{
  "error": {
    "code": "ORDER_NOT_PAYABLE",
    "message": "order cannot be paid in its current state",
    "details": [{"field": "state", "reason": "cancelled"}],
    "retryable": false
  },
  "request_id": "req_123"
}
~~~

HTTP 状态表达协议层结果，业务 code 表达稳定的可处理原因；不要把数据库异常、堆栈或供应商秘密直接返回。统一定义：

- 认证失败、无权限、找不到、冲突、限流、校验失败、依赖失败和未知错误的 HTTP 映射；
- code 的命名、稳定性、文档和客户端处理；
- retryable、Retry-After、幂等键和去重语义；
- request_id/correlation_id 如何贯穿日志、异步任务和外部调用。

### 版本和兼容

- 公共字段优先向后兼容，新增可选字段，避免重命名/改变含义；
- 破坏性变化使用显式版本、迁移窗口或双读/双写；
- 事件 schema 带版本和生产者责任，消费者要能处理未知字段；
- 记录弃用时间、客户端覆盖范围和移除条件；
- 契约测试验证真实序列化、状态码、错误码和权限，而不是只测内部对象。

## 配置、秘密与可观测性

- 配置按环境注入，代码仓库只保存安全的默认值和 .env.example；
- 秘密进入 Secret Manager/受控环境变量，禁止提交、日志打印和错误响应泄露；
- 启动时校验必需配置，区分可热更新和需重启的配置；
- 结构化日志包含时间、级别、服务、版本、request_id、用户/租户的安全标识和结果；敏感数据脱敏；
- 指标覆盖流量、错误率、延迟、队列积压、任务重试、资源、关键业务结果和发布版本；
- 追踪跨 API、数据库、队列和外部依赖传播 correlation_id；
- liveness 与 readiness 语义分开，依赖不可用时不要把活着的进程误报为就绪；
- 每个告警有阈值、责任人、运行手册和解除条件。

## 机制门禁

回到 05-architecture-design.md 的 Architecture Ready 门禁前，本文件涉及的每一项都要有结论：

1. 每个机制标记为“现在必须有 / 明确不需要 / 由风险触发”，并写明驱动它的 A-ID、Q-ID 或风险；
2. “现在必须有”的机制有具体决策、失败语义和验证方式，不是只写下机制名称；
3. 公共契约的错误信封、版本策略和兼容窗口已确定；
4. 秘密、配置和敏感字段的处理边界已确定，且不依赖“记得不要提交”；
5. 每个机制至少有一条计划中的证据（合同测试、集成测试、重放实验或启动探针）带到 09-testing-review-integration.md。

机制决策同样写入 ADR；实现细节留给 08-implementation-tdd.md，不要在本阶段提前写生产代码。
