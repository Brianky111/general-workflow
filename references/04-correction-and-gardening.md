# 纠错下沉与主动除草

在 Agent 参与日常开发后，代码库像一座持续生长的花园：每一次人工纠错如果不转化为代码层约束，就会在下一轮对话被重犯；每一个留在仓里的坏样例如果不及时清理，就会像杂草一样被后续 Agent 指数级复制。

## 倒金字塔纠错阶梯

本节是本工作流中**纠错沉淀优先级阶梯的唯一权威**，其他文档只引用本节。

1. **纠错按倒金字塔从上到下尝试，最后才写 AGENTS.md**：每次你发现自己第二次提醒 Agent 同一个问题，立刻停下来做下沉（参见 `vendor/pstack/skills/principle-encode-lessons-in-structure/SKILL.md`），而不是给提示词加一句“请务必注意”。
2. **第一步：收窄或重写 API，让错误写法在结构上不可表达**：优先问“能不能改掉接口签名、私有化内部字段或合并原子操作，使错误调用连编译/类型检查都过不去？”能靠结构消灭的错，不留给检查器。
3. **第二步：加一条带根因修复提示的静态检查或依赖规则**：当语言类型表达不了时，优先加进目标项目的原生 Lint / AST 依赖检查并接进 `check_command`，再用 `.guardrails/config.json` 的 `forbidden_primitives` / `boundary_rules` 兜底，并按 `02-codebase-guardrails.md` 写明该改用哪个接口。
4. **第三步：清理仓库里同源旧坏样例，阻止后续 Agent 模仿**：规则写完立刻在仓内搜索同类旧写法并清理，或收紧棘轮上限。留着坏样例，下一批 Agent 还会照抄并试图用注释绕过检查。
5. **第四步：补运行时验证、PBT 或形式化不变量**：若问题是时序、并发或用户体感偏差，把复现脚本固化进 `verify_cli` / `verify_skill`，必要时补属性测试或状态机模型检测（见 `03-verification-and-artifacts.md`）。
6. **第五步：只有无法编码的主观判断才写入极简 AGENTS.md**：仅保留领域术语、产品审美取舍、外部协作流程等静态分析和运行时测试实在表达不了的内容。

反例对比：发现 Agent 在界面组件里直接写了 `setTimeout` 修竞态。差的做法是在 `AGENTS.md` 加一行“不要在 UI 里乱用定时器”；好的做法是封一个 `scheduleDebouncedAction` 原子 API → 用原生 Lint 或 `forbidden_primitives` 禁用裸 `setTimeout` → 把现有 3 处旧 `setTimeout` 改掉 → `AGENTS.md` 一字不加。

## 历史错误聚类与旧错例证伪（/correct 闭环）

日常遇到反复纠错或接手问题不断的仓库时，直接按 `vendor/pstack/skills/correct/SKILL.md` 与 `vendor/pstack/skills/principle-fix-root-causes/SKILL.md` 执行外科手术式闭环，而不是只记笔记：

1. **聚类证据**：读取近期 git commits、reverts、评审意见、指令文件以及 workaround 注释；**同一错误类在记录中出现 ≥ 2 次即正式立项**，按影响面排序并逐类修复（每类一个独立 commit）。
2. **直击根因与最高层**：假设贡献者只看打开的那几个文件并模仿最近样例——优先改目标仓架构（单状态所有者、唯一做法、删旧 API）、再收窄类型、再加报错直指替代接口的原生 Lint（若旧坏模式极普遍，可先卡住增量不允许新增），并用 `vendor/pstack/skills/no-comments/SKILL.md` 清理衍生出的借口注释。
3. **强制旧错例证伪回放**：每一条新加的类型约束、原生 Lint、边界规则或回归测试，交付前**必须用过去一次真实犯错的提交或复现片段验证它会红灯拦截**；如果旧错还能绿灯通过，这条检查无效，必须重写。
4. **本地与 CI 同命令，例外带期限**：本地与 CI 运行同一条 `check_command`；确有无法避免的例外，必须标在具体违规行上并注明原因、过期日期与人工批准人。
5. **收尾汇报三要素**：每修完一类，说明该类的历史证据、选定的倒金字塔层级，以及为什么更高一层不能消除它。

## 反深潜熔断与停放区（Anti-Rabbit-Hole）

对 Vibe Coding 而言，“越改越深、最后主线搁浅”比写得慢更致命。除草与纠错必须严格服从交付节奏：

1. **主线高于重构**：核心主流程尚未跑通或本轮垂直切片未交付前，**严禁**自发开启多轮纯内部重构（如全仓分层搬家）或漫无目的的全仓除草；护栏、`/correct` 与 `/no-comments` 只允许用来解决**挡住当前主线**或**已经反复绊倒 ≥ 2 次**的真痛点。
2. **顺手发现进停放区，严禁当场深挖**：推进主线时顺手撞见的非阻塞旧债、P2/P3 边缘毛刺或样式微调，**只许写一行记入停放区**（在本轮汇报末尾或 `.guardrails/parking-lot.md` 挂号），绝不允许当场顺藤摸瓜扩成新分支或重写无关模块。
3. **单模块 2 轮止损线**：同一个内部模块连续修改超过 2 轮仍拿不出用户可观察的结果或无法过线，必须立即停下，向用户汇报卡点或切回极简替代方案。
4. **拒绝重型脚手架失衡**：不为十几行小改动配套编写数百行特征测试或繁重兼容层，保持“最小可验证变动”。

## 主动除草与棘轮协议

旧工程规范常要求“改功能时绝对不要碰旁边的旧代码”，这在人工慢速迭代时代能防范围膨胀，但在 Agent 时代有个致命副作用：旧的 workaround 和脏写法本身就在 Agent 的上下文窗口里，留着它们就会持续诱发新烂代码。因此需要区分**安全除草**与**改行为**：

- **安全除草（加规则即清理）**：在已有检查全绿保护下，把明确违反新护栏的同源坏模式机械替换成受控新 API，并按“先减后加”顺手拔除冗余透传壳、历史兼容垫片或拆分超长巨石文件（`file_limits`），不改变公开接口、持久化结构与用户可观察结果，应随加规则一并清掉。
- **涉及行为变更的清理**：如果拔除旧代码会改变接口语义、兼容窗口或用户可见流程，走 `01-intent-and-invariants.md` 确认意图后按正常功能改动并交验证产物。

当接手一个体量较大的老仓库、无法在单轮把几十处旧债全部拔干净时，启用**棘轮协议（Ratchet）**，统一覆盖 `escape_hatches`、`anti_patterns` 与 `file_limits` 三类计数：

1. 初始可用 `repo_guard.py --scan` / `--init` 将当前真实数量锁定到 `.guardrails/config.json` 各自的 `max_allowed`；
2. 任何新代码绝对不允许增加总数——多 1 条直接让 `repo_guard.py` 报错拦截；
3. 每清理掉一批旧逃生舱、反模式或拆瘦超长文件，顺手把对应 `max_allowed` 往下调到当前新数值（`repo_guard.py` 发现实际数量低于上限时会提醒下调）；
4. 直到三项 `max_allowed` 均降至 `0`，仓库进入零旧债基线，具备开启外循环自动化的资格。

## AGENTS.md 瘦身规则

`AGENTS.md` 不是无限增长的错题本，而是对照表。在 `AGENTS.md` 维护一张简洁的 **`Rule | Enforcer`** 表，把每一条规则和实际拦截它的机制（类型、原生 Lint、`repo_guard` 规则、测试或 `unenforced`）绑定起来：

- 当用户再次纠正某条已写在表里但 `Enforcer` 为 `unenforced` 的规则时，说明自然语言已经失效，必须在**同一个变更里**按倒金字塔把它推进到结构/类型/Lint 层；
- 一旦某类错误在结构上已经完全不可能发生（例如旧 API 已删、类型已卡死），**立即从表和文档里删掉这条规则**，省下上下文给真正的主观判断。

`repo_guard.py` 默认将所有受检文档（含根目录及子目录的 `AGENTS.md`）限制在 `6,000` 字节以内，并在出现 3 条以上“禁止/不要/never/must not”自然语言禁令时发出警告，提示你把它们下沉成可执行护栏。

## 除草门禁

一次纠错或除草工作收尾前，核对：

1. 重复出现的问题已尽量通过目标仓 API 收窄、强类型或原生确定性检查解决，而不是只多写了几行自然语言提示；
2. 每条新建检查规则均经过**真实历史错例或破损变更的证伪回放**（旧错必红、当前必绿），并带有清楚的根因修法与同源旧坏样例清理；
3. `AGENTS.md` 体积未超标，使用 `Rule | Enforcer` 表追踪且已删去已被结构消灭的过时禁令；
4. 运行 `repo_guard.py --run-check` 退出码为 `0`，且行为改动部分已更新 `.guardrails/verification.md`。
