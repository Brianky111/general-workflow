# 架构设计阶段指南

架构不是先画一张漂亮的图，而是根据已确认的结果、质量属性、数据和运行边界，做一组可解释、可验证、可重评的选择。附件中的架构、脚手架、TDD、测试和部署思路在这里合并为一条架构驱动的决策链。

## 目的与入口

目的：在真实编码前冻结高代价边界，避免系统形态、数据所有权、公共接口或安全策略在实现中无意中形成。

入口：

- 需求、场景、范围和非目标已有稳定的 R-ID/A-ID；
- 质量目标、约束和高风险未知已记录；
- 项目画像已给出产品形态、运行单元、团队和风险档位。

架构输出不必是长文档。低风险项目可以用一页决策表和一张拓扑图；高风险项目需要 ADR、数据字典、威胁/容量/恢复验证计划。

## 决策顺序

按从贵到便宜、从不可逆到可替换的顺序做决定：

1. **架构驱动**：列出必须满足的用户结果、质量目标、约束和风险；
2. **系统形态**：决定进程、worker、服务、事件和客户端边界；
3. **边界与所有权**：决定模块职责、依赖方向、数据归属和公共契约；
4. **运行时拓扑**：决定请求、任务、存储、外部依赖、故障域和扩缩容；
5. **数据模型**：决定实体、不变量、状态、一致性、迁移和保留；
6. **关键机制**：决定身份、异步、幂等、重试、事务、缓存、限流和文件等；
7. **API/事件契约**：决定交互风格、版本、错误、可重试和兼容策略；
8. **技术栈**：把前述约束落成语言、框架、数据库、消息和观测组件的具体版本；
9. **部署形态**：决定环境、产物、迁移、发布、监控、回滚和恢复；
10. **验证计划**：为每个高代价假设指定最小实验或真实切片证据。

公共接口、数据所有权、安全边界和部署单元是高代价决策；私有类名、内部抽象和未来插件点通常可以延后。

第 6、7 步（关键机制与 API/事件契约）在 05a-mechanisms-and-contracts.md 中展开；本文件负责判断哪些机制现在必须决策，以及把结论接回技术栈和部署选择。

## 系统形态选择

| 候选形态 | 适用信号 | 主要优点 | 主要代价/触发条件 |
| --- | --- | --- | --- |
| 简单单体 | 一个核心领域、一个团队、单一发布节奏、低风险 | 开发和部署最简单，事务和调试直接 | 模块边界弱；出现独立扩缩容或所有权后需加强 |
| 模块化单体 | 多个业务模块但共享发布、数据或团队 | 保留单体运维成本，同时显式隔离模块 | 需要依赖规则和边界测试，不能靠文件夹自律 |
| 应用 + worker | 请求路径与长耗时、重试或资源密集任务不同 | 用户响应稳定，可独立扩缩容任务 | 队列、幂等、状态查询、失败恢复和运维成本 |
| 多服务 | 独立团队/所有权、部署、扩缩容和故障域都真实存在 | 服务可独立演进和隔离 | 网络、分布式一致性、合同测试和值班复杂度 |
| 事件驱动 | 需要解耦多个消费者、异步传播或事件审计 | 扩展消费者、削峰和松耦合 | 事件版本、重复、顺序、可观测性和最终一致性 |
| 多客户端共享 API | Web、移动、第三方或内部客户端共享业务能力 | 统一规则和数据契约 | 公共兼容、限流、版本和安全要求更高 |

默认选择能满足当前质量目标的最简单形态。只有独立部署、独立扩缩容、独立数据所有权、独立发布节奏或明确故障隔离需求同时有证据时，才拆成服务。不要因为团队人数、流行架构或“以后可能扩展”单独拆分。

## 目录组织与模块边界

### 三种常见组织方式

**直接分层**：按技术角色聚合，例如 controllers、services、repositories、models。适用于单一领域、代码量小且团队需要快速定位同类技术文件的项目。要避免 service 层变成所有业务的垃圾场。

**纯模块化**：按业务能力聚合，例如 users、orders、catalog。适用于业务域边界清楚、团队按领域协作的项目。模块内部可以先保持扁平，不要为了“完整”创建空 domain/application/infrastructure 层。

**模块化 + 分层**：大方向按业务模块，模块内部按 domain、application、infrastructure、interfaces 分层。适用于多个变化边界、复杂规则、需要替换外部适配器或高风险测试的项目。

示例：

~~~text
modules/
  orders/
    domain/           # 实体、值对象、不变量；不依赖框架或数据库
    application/      # 用例、端口、事务边界
    infrastructure/   # ORM、消息、第三方适配器
    interfaces/       # HTTP、CLI、订阅者、序列化
  identity/
  shared/             # 少量稳定的跨模块原语，不放业务规则
bootstrap/            # 配置、组合根、路由和进程启动
tests/
~~~

混合结构也可以成立：例如核心订单模块使用模块化加分层，后台管理等低复杂度区域使用直接分层；必须记录适用边界和未来合并/拆分条件。

### 依赖规则

- 业务规则依赖抽象和输入，不依赖 HTTP、ORM、队列或云 SDK；
- 外层可以依赖内层，内层不能反向依赖具体外层；
- 模块之间只通过公开用例、端口或事件通信，不直接读取彼此的表或内部类；
- 一个数据事实只有一个拥有者；共享查询通过公开读模型、API 或事件同步；
- shared 只收纳稳定、无业务归属的原语；第二次复制和第三个调用方出现前不要抽象；
- 组合根负责注册真实实现，测试替身不能形成平行生产路径；
- 依赖图不能有循环；若出现循环，先重新划分职责或引入明确的端口/事件；
- 目录结构服务于边界，不为未来模块、层或服务创建空目录。

## 运行时拓扑

至少画出以下节点及连接：

~~~text
client
  -> ingress/API
      -> application module
          -> domain rules
          -> database (owner)
          -> external provider
      -> queue -> worker -> database/provider
observability: request id -> logs + metrics + traces
~~~

为每条连接标出同步/异步、超时、重试、认证、数据流向和故障后的用户可见结果。为每个部署单元标出：

- 进程和端口；
- 依赖的数据库/缓存/队列；
- 扩缩容指标；
- 健康检查和就绪条件；
- 故障隔离、降级和恢复方式；
- 配置与秘密来源。

拓扑图不是容量证明；高风险容量假设必须在 04 阶段的实验或 07 阶段的真实切片中验证。

## 核心数据模型

按五层逐步落地：

1. **概念模型**：业务中的实体、关系、生命周期和术语；
2. **行为模型**：实体能做什么、状态如何转换、哪些不变量必须始终成立；
3. **所有权模型**：哪个模块写入事实、谁负责迁移/备份/删除/审计；
4. **一致性模型**：同一事务内必须强一致的事实、可最终一致的投影、允许的暂时状态；
5. **物理模型**：表/集合、主键、外键、索引、分区、TTL、加密和迁移脚本。

每个关键实体至少记录：

~~~markdown
| entity | owner | identity | states | invariants | sensitive_fields | consistency | retention | migration |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Order | orders | immutable id | draft/paid/cancelled | total >= 0; one payment | address | transaction | 7 years | expand/contract |
~~~

值对象用于表达金额、地址、时间范围等带规则的值；不要用一串裸字符串让规则散落在控制器。状态转换应列出合法事件、非法事件、并发版本和幂等键。

数据决策还要明确：

- 主键/外键和跨模块引用是否允许；
- 软删除还是硬删除，删除请求如何传播；
- 审计记录包含什么、谁能读、能否篡改；
- 备份、恢复点目标（RPO）和恢复时间目标（RTO）；
- 数据库迁移是否支持旧代码与新代码短暂共存；
- 读模型、缓存、搜索索引和报表如何从权威事实重建。

## 关键机制与契约

对以下每一项标记“现在必须有 / 明确不需要 / 由风险触发”，并写明驱动它的 A-ID、Q-ID 或风险：

- 身份、授权、租户边界和审计；
- 异步任务、幂等、重试、死信和补偿；
- 事务边界、并发控制、缓存、限流和文件处理；
- API/事件风格、统一错误信封、request_id、版本与兼容；
- 配置、秘密、日志、指标、追踪、健康检查和告警。

标为“明确不需要”的项目在此写下理由即可。只要有任意一项是“现在必须有”或“由风险触发”，加载 05a-mechanisms-and-contracts.md 完成该项决策，再回到本文件继续技术栈和部署选择。

## 技术栈选择

把“喜欢”转换成可比较的候选：

| 维度 | 问题 |
| --- | --- |
| 结果适配 | 能否直接支持目标入口、数据和质量目标？ |
| 团队能力 | 团队能否调试、升级、值班和招聘？ |
| 生态与成熟度 | 依赖、文档、安全更新和许可证是否可靠？ |
| 运行成本 | 计算、存储、托管、监控和迁移成本？ |
| 可替换性 | 供应商锁定、数据可导出、边界是否清楚？ |
| 交付速度 | 官方脚手架、测试工具和本地开发是否顺畅？ |

对语言、框架、数据库、消息、缓存、部署和观测组件写具体版本、选择理由、接受的代价和替换条件。不要因为“最新”或“微服务”本身加分。

### 数据与基础设施匹配

先从访问模式和不变量选择数据技术，再从品牌选择产品：

- 关系型数据库适合事务、不变量、关联查询和成熟迁移；文档数据库适合边界清楚、聚合读取和 schema 变化快的文档；
- 键值、时序、列式或搜索引擎只在访问模式、容量或检索能力明确需要时引入；
- 消息系统要有消费者、重放、顺序或削峰的实际场景；缓存要有命中目标和失效策略；
- 多种持久化技术的每个事实必须有唯一权威来源、同步/重建方法和额外运维责任；
- 选择托管服务、容器平台或自建组件时，比较数据导出、区域、SLA、成本、升级和故障处理，而不是只比较功能列表。

技术栈表应把“需求/质量属性→组件→版本→验证证据”连起来，避免先定品牌再寻找使用场景。

## 部署拓扑与恢复

设计 dev、staging、production 的隔离和晋级路径：

- 哪些配置/数据可以共享，哪些必须隔离；
- 构建产物是否不可变、如何关联提交、依赖锁文件和 SBOM；
- 迁移是应用启动前、独立 job 还是双阶段展开/收缩；
- 备份频率、加密、恢复演练和数据校验；
- 滚动、蓝绿、金丝雀或分批发布的触发条件；
- 回滚是切换代码、前滚兼容迁移，还是执行补偿；
- 依赖故障时的降级、维护页面和用户通知。

具体发布和运行清单见 10-release-operations.md。

## ADR 与验证计划

每个高代价决策用一个短 ADR 表达：

~~~markdown
# ADR-0001: <decision>
- status: proposed | accepted | superseded
- drivers: <需求/质量/约束/R-ID/Q-ID>
- candidates: <候选及关键差异>
- decision: <选择>
- tradeoffs: <接受的代价和未解决风险>
- validation: <实验、切片、测试或运行证据>
- revisit_when: <何时重新评估>
- owners: <责任人>
~~~

架构验证计划至少映射：

- 每个高风险假设 → 一个实验或第一条切片证据；
- 每个公共边界 → 一个契约/集成场景；
- 每个数据不变量 → 单元/集成/迁移证据；
- 每个安全边界 → 未授权、越权、审计和秘密检查；
- 每个发布/恢复假设 → staging 演练或可执行 runbook。

## Architecture Ready 门禁

进入 06-scaffolding-and-ci.md 前，必须能回答：

1. 为什么选择当前系统形态，而不是更复杂或更简单的候选？
2. 模块职责、依赖方向、数据所有权和公共边界在哪里？
3. 核心实体、状态、不变量、一致性和迁移如何成立？
4. 鉴权/授权、异步、幂等、错误码、观测和恢复哪些现在必须做？被标为“现在必须有”或“由风险触发”的项目是否已在 05a-mechanisms-and-contracts.md 中得到结论？
5. 技术栈有具体版本、团队可维护理由和替换条件吗？
6. 哪些高代价假设要由实验或第一条垂直切片验证？
7. 还未决的问题是否真的会改变行为、范围、数据、安全、兼容、成本或部署？

退出产出可以是架构决策表、ADR、目录草图、数据模型、拓扑和验证清单的组合，但每项都必须有权威位置，不能互相漂移。
