# 技术栈选型与深模块架构地图

本文件衔接 `01-intent-and-invariants.md`（已通过 Frontier Grill 收敛需求与术语），在写业务源码前选定最适合的工程技术栈，并用深模块切分与可编译负不变量生成根目录 `ARCHITECTURE.md`。

## 架构规划入口闸（Scope Challenge）

先确认任务是否真需要完整架构规划，避免小改大作：

- **直接退回简路**：若技术栈已定、单进程单库且预期切片 `<= 3` 个，或仅涉及局部代码重构/两方案选型，直接改用 `vendor/pstack/skills/architect/SKILL.md` 做局部方案对比，随后跳过 `01a`/`01b` 进入 `02-codebase-guardrails.md`。
- **进入完整规划**：涉及 **0→1 新项目选型**，或现有系统需要变更**技术栈、顶层模块拓扑、数据所有权或部署单元数量**时，按本文件与 `01b-dataflow-and-contracts.md` 推进。
- **已有仓库先行取证**：旧仓启动架构演进前，先运行 `repo_guard.py --root "<目标项目绝对路径>" --scan` 摸清当前技术栈、巨石模块与旧债基线，不凭印象设计。

## 技术栈选型计分卡（Stack Scorecard）

融合 `gstack` 务实工程选型与解交织透镜，**严禁按热度选型**：

1. **硬约束先行淘汰**：先以运行平台、合规要求、团队维护边界与既有基础设施筛掉不可行选项，仅保留 **2–3 套候选栈**。
2. **必含两套基准线**：候选中必须包含 **1 套“无聊成熟默认（Boring Default）”**（生态最稳、运维简单）与 **1 套“最小可行栈（Minimal Viable）”**（依赖最少）。默认采用**单部署单元 + 单主库**（如 SQLite/PostgreSQL），没有实测瓶颈或硬隔离需求不拆微服务。
3. **六维计分核对**（每个结论必须标注证据口径 `实测 / 官方文档 / 推断`，外部版本、配额与限制必须查证后再写）：

| 评估维度 | 必须回答的具体工程问题 |
| --- | --- |
| **1. 业务与规模匹配** | 当前吞吐、并发、离线/实时诉求下，这套栈是否刚好够用而非大炮打蚊子？ |
| **2. AI 倒金字塔承载度** | 类型与编译报错能否精准指明修法？目录依赖边界能否机检（注意 `repo_guard.py` `boundary_rules` 原生覆盖 Python/JS/TS/Rust；其他语言或含路径别名的 monorepo 必须明确挂载原生边界 Linter）？`check_command` 冷启动是否 `< 5s`？能否无头驱动写出真 `verify_cli`？语料与 API 是否稳定？ |
| **3. 数据层不可逆代价** | 事务一致性、备份恢复与后续 Schema 迁移是否可控？ |
| **4. 解交织拷问（De-complecting）** | 直白写出该框架为了“上手顺手（Easy）”，到底把哪两件事（如状态、时序、传输、身份、UI 渲染）暗中缠在了一起？将来剥离成本多大？ |
| **5. 运维与外部依赖半径** | 上线运行最少需要多少个外部进程、密钥、托管服务与升级风险？ |
| **6. 原型决胜（Prototype Tie-Breaker）** | 若某关键未知在纸面分不出胜负，按 `vendor/pstack/skills/poteto-mode/playbooks/prototype.md` 在隔离临时目录做带切换开关的实测原型，用实测数字裁决，绝不空猜。 |

仅对满足“难逆转 + 无背景会困惑 + 存在真实取舍”的选型落盘 **`docs/adr/0001-stack.md`**（`<= 3,000`B），把淘汰方案与拒绝理由写死。

## 系统级 Design It Twice 与深模块切分

选定栈后切分系统模块（遵循 Ousterhout 深模块思想与 `codebase-design` 接缝纪律，**深度按目录公开入口的窄度与调用杠杆计，绝不按单文件行数堆砌**，单文件仍受 `file_limits: 600` 约束，深模块内部可拆私有小文件但只暴露极窄入口）：

1. **System-Level Design It Twice**：针对核心需求画出**两套结构真不同**的模块划分草图（如按业务能力域切 vs 按数据管线/状态生命周期切），选取 3 个高概率未来变更场景，逐一数清两种划分下“各需跨改几个模块”并用信息隐藏度做胜负手。
2. **深模块五栏审查与删除测试**：每个候选顶层模块必须写清：
   - `一句话职责 | 唯一公开入口（Seam） | 隐藏的内部决策（如缓存/重试/格式/并发） | 拥有的状态 | 允许依赖的模块`
   - **浅模块拦截**：若“隐藏的内部决策”一栏为空，或删除该模块后复杂度只是原样落回调用方而未省掉认知负担，即属纯透传浅模块，当场合并或删掉。
   - **双适配器原则**：只有一个具体实现时不预抽抽象接口或 Adapter；真实出现第二个变体时再沿同一 Seam 抽离。
   - **禁时序分解与禁预建空壳**：禁止按执行先后拆成 `step1_loader / step2_processor`；模块地图描述目标态，切勿提前建一堆空目录。
3. **机械触发条件参考（按信号加载，禁止无触发预读）**：
   - 出现 `>= 2` 个有状态存储或部署单元、消息队列/后台任务、支付/Webhook 等有副作用外部 API、离线或多端同步，或缓存承载正确性 → 加载 **`01c-distributed-and-sync.md`**；
   - `irreversible_boundaries` 含资金/账务/不可恢复数据，或涉及自研存储/协议/硬实时引擎 → 加载 **`01d-high-assurance-bounds.md`**；
   - 前端含乐观更新、实时协作、离线编辑，或客户端同时持有 `>= 3` 类状态源 → 加载 **`01e-client-state-flow.md`**。

## 根目录 ARCHITECTURE.md 规范

参考 `matklad` 鸟瞰规范，在仓库根目录写入 **`ARCHITECTURE.md`**（`<= 6,000`B，将接入 `prose_files` 接受字节与禁令门禁）：

1. **系统鸟瞰（Bird's-Eye View）**：一段话讲清系统接收什么输入、经过哪几层主路径、持久化到哪里、由几个部署单元运行。
2. **Codemap（目录与核心符号地图）**：列出顶层模块目录（跨边界目录段名保持全局唯一，方便 `boundary_rules` 路径段精确匹配）与可全局搜索的核心类型/入口符号名。**严禁写具体文件行号或 `#L123` 链接**（`repo_guard.py --check-arch` 与 `prose_files` 检查会直接报错拒收）。
3. **架构负不变量表（`<= 7` 条，“谁绝不能认识谁 / 哪层绝不做什么”）**：每条必须绑定可执行编译落点（`boundary_rules` ID、`forbidden_primitives` ID 或原生 Linter 规则名）。
   - 已预编译进 `docs/arch/guardrails-fragment.json` 或原生 Lint 的条目，在文中写成“`[rule-id]` 正向边界表述”（避免触发 `prose_files` 的 3 行禁令告警）；
   - 暂无法自动机检的条目必须明确前缀 **`UNCOMPILED:`** 并说明人工/评审落点——让 `repo_guard.py` 告警成为未编译架构债的精确计数器。

离开本文件进入 `01b-dataflow-and-contracts.md` 前确认：

1. 已写就 `docs/adr/0001-stack.md`（含 2–3 套对比、AI 倒金字塔承载度与解交织拷问）及根目录 `ARCHITECTURE.md`（无行号引用、`<= 6,000`B）；

3. `ARCHITECTURE.md` 中全部负不变量均已指明编译目标或显式标注 `UNCOMPILED:`，且触发的条件参考已按信号识别。
