# 条件深化：前端多源状态解交织与交互流

本文件吸收 Rich Hickey 的解交织（De-complecting）思想与前端状态分治原则，解决 Vibe Coding 前端中最常见的“多布尔标志同步打架、URL 与缓存状态两份拷贝撕裂、乐观更新失败后假成功”问题。

## 触发信号

仅当应用前端符合以下任一信号时加载（简单静态展示页或常规表单 CRUD 无需加载）：

- 存在**乐观更新（Optimistic UI）**、并发流式生成（AI 流式输出+中断/重生成）或**多步骤富交互画布/编辑器**；
- 存在**实时多人协作或离线草稿/本地缓存回写同步**；
- 客户端同时持有 **`>= 3` 类不同来源的状态**（如服务端数据 + URL 查询参数 + 本地草稿 + 实时推送）。

## 四类客户端状态严禁混仓（解交织）

架构设计阶段必须把客户端状态拆成互不纠缠的四类并指明各自唯一权威源，**禁止用 `useEffect` 在多个 Store 之间手工抄来抄去**：

| 状态类别 | 唯一权威源 | 典型内容 | 严禁的错误做法 |
| --- | --- | --- | --- |
| **1. 服务端缓存态** | 查询缓存层（如 Query/SWR/服务端快照） | 列表数据、实体详情、权限配置 | 拷贝一份进全局 Store 并在多处手动 `setState` 同步 |
| **2. URL / 路由参数态** | Router URL（SearchParams / Path） | 当前页码、筛选条件、排序、选中 ID | 把筛选条件藏在内存态导致刷新/分享链接丢失状态 |
| **3. 瞬时交互态** | 局部组件作用域 | Tooltip、Hover、弹窗显隐、拖拽临时坐标 | 提升成全局状态污染全树重渲染 |
| **4. 本地草稿与撤销栈** | 明确有界本地 Store / IndexedDB | 未提交表单、富文本编辑历史、离线队列 | 未区分“已保存服务端版本”与“未提交脏草稿” |

- 派生状态（如选中数量、过滤后视图、校验是否通过）一律在渲染或 selector 处**纯计算派生**，绝不单独存成同步字段。

## 纯函数状态机与乐观回滚语义

1. **用判别联合状态机取代多布尔标志**：禁止出现 `isLoading && isError && hasRetried` 这类 8 种组合里有 5 种非法的散落布尔值；在 `docs/arch/contracts.md` 用 `status: 'idle' | 'pending' | 'streaming' | 'failed' | 'ready'` 枚举显式建模，并用纯函数 `(state, event) => nextState` 表达合法转移。
2. **乐观更新必须定义对账与可见回滚**：凡先改 UI 后发请求的乐观操作，必须在 `docs/arch/dataflow.md` 写明：唯一客户端临时 ID 生成规则、服务端权威版本到达后的替换对账路径，以及请求失败时**可被用户感知的回滚与错误提示**（禁止静默吞错留下幽灵数据）。

## 客户端状态门禁

回填 `01b-dataflow-and-contracts.md` 前核对：

1. 前端状态已清晰划入四类职责，无“URL/服务端数据又在全局 Store 手工镜像同步”的双真相源；
2. 复杂异步或编辑交互已用判别联合状态机建模，且派生值均由单一真相计算得出；
3. 乐观更新与流式中断均已补齐对账逻辑、失败回滚可见反馈及对应验证钩子。
