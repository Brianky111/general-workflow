# 项目画像与流程深度

项目画像的作用是决定需要多深的架构、验证和发布流程，不是用“项目大/小”给技术方案贴标签。尤其不要把“小团队=单体”“大团队=微服务”当成默认规则。

## 画像维度

在开始架构前，逐项填写当前已知事实；不知道的内容标成未知，并在风险阶段决定是否需要实验。

| 维度 | 要回答的问题 | 对架构的影响 |
| --- | --- | --- |
| 产品形态 | Web、移动端、桌面、CLI、库、数据管道、内部工具还是平台？ | 入口、交付方式和客户端边界 |
| 用户与入口 | 谁使用？直接用户、管理员、合作方还是服务？通过什么入口？ | 鉴权、API、体验和可观测性 |
| 业务域 | 一个核心能力还是多个变化速度不同的领域？ | 模块边界和所有权 |
| 运行单元 | 一个进程、应用+worker、定时任务、服务群还是边缘组件？ | 部署、扩缩容和故障隔离 |
| 数据 | 关键实体、规模、增长、敏感级别、读写模式、保留期？ | 数据库、分区、迁移、一致性和备份 |
| 外部依赖 | 支付、身份、消息、搜索、文件、第三方 API？ | 超时、重试、合同和替代方案 |
| 团队与所有权 | 谁开发、运维和审批？团队边界是否真实存在？ | 服务拆分、代码所有权和发布节奏 |
| 生命周期 | 一次性实验、内部长期工具、公开产品、受监管系统？ | 维护投入、兼容、审计和恢复 |
| 风险 | 安全、隐私、合规、金钱、生命、声誉或不可逆数据操作？ | 流程档位和独立验证 |
| 交付节奏 | 需要频繁独立发布，还是单一批次即可？ | 分支、流水线和部署策略 |

## 规模判断：看负载和边界，不看文件数

在画像中单独记录规模信号，但不要把它们机械相加成“必须微服务”的结论：

- **用户规模**：活跃用户、组织/租户数量、峰值并发和地域；
- **数据规模**：初始量、增长率、单条大小、查询/写入比例和保留期；
- **业务规模**：核心领域数量、规则密度、状态复杂度和变化速度；
- **运行规模**：进程、worker、定时任务、外部调用和故障域数量；
- **协作规模**：团队边界、代码所有权、独立发布和运维责任；
- **风险规模**：一次错误的资金、隐私、合规、声誉和恢复代价。

小代码量也可能有高风险或高并发；代码量大但单团队、单领域、同一发布节奏，仍可能适合模块化单体。规模判断的产物是“需要哪些隔离和证据”，不是一个预设的服务数量。

## 形态信号

记录“事实→信号”，不要直接从名词跳到结论：

- 需要独立扩缩容、独立故障域或独立发布节奏，才是拆分运行单元的信号。
- 存在真实的团队边界、数据所有权和接口责任，才是拆分服务的组织基础。
- 一个核心领域、一个团队、一个数据库和同一发布节奏，通常从简单单体或模块化单体开始更经济。
- 同步请求中有长耗时、可重试或资源密集工作时，考虑应用加 worker；不要因为“以后可能异步”就先引入消息平台。
- 多个客户端共享稳定公共契约时，优先先定义 API/事件边界，再判断是否需要独立服务。
- 高敏感数据、不可逆写入、严格可用性或审计要求，即使代码量小，也应提高验证深度。

## 流程档位

### LEAN

适用信号：单团队、低风险、单一运行单元、无公共兼容承诺、可恢复数据、少量外部依赖。

最小要求：

- 一页需求/场景/范围；
- 轻量架构决策记录；
- 真实入口的第一条垂直切片；
- formatter、lint、测试、构建和基础 CI；
- 至少一个可执行的发布/回滚说明。

### STANDARD

适用信号：多个业务模块、持久化数据、异步或第三方依赖、多个环境、多人协作或持续发布。

增加要求：

- 明确模块/数据所有权；
- 可度量质量目标和风险实验；
- ADR、迁移策略、合同或集成测试；
- staging、观察窗口、告警和恢复演练。

### HIGH-RISK

适用信号：支付/资金、隐私或合规、公共 API、不可逆迁移、严格 SLA、复杂并发、跨团队共享契约或高恢复成本。

增加要求：

- 独立安全/架构评审或职责分离；
- 威胁建模、容量/性能基线、兼容性证明；
- 备份恢复和迁移演练；
- 分批/灰度发布、审计记录和明确值班责任；
- 风险实验及其通过条件必须在实现前完成。

档位只决定最低证据，不限制用户主动要求更严格的流程。

## 画像输出模板

~~~markdown
# Project Profile
- status: IDEA | DEFINED | ...
- shape: <产品形态>
- users/entrypoints: <用户与入口>
- problem/outcome: <当前要解决的问题和核心结果；指向目标合同或原始请求>
- domains: <业务域及变化边界>
- runtime units: <进程/worker/任务/服务>
- data: <实体、规模、敏感度、一致性>
- external dependencies: <依赖及所有权>
- team/owners: <开发、运维、审批>
- lifecycle: <实验/长期/公开/受监管>
- delivery cadence: <发布节奏>
- risk tier: LEAN | STANDARD | HIGH-RISK
- scale_signals: <用户/数据/业务/运行/协作/风险规模>
- unknowns: <必须验证的未知>
- chosen depth: <为何采用该档位>
~~~

## 画像门禁

至少要能说明项目形态、目标用户/入口、问题与核心结果、风险档位，才能进入下一阶段。若这些仍未知，先补最小事实；会改变需求含义的未知按下面的回流规则处理。

## 拆解失败与 P0 回流

P0 也是重新核实原始意图的入口。任意阶段发现以下情况，先回到本节，再决定如何继续拆解：

- 需求或场景中的用户、使用情境、入口、核心结果与原始请求不一致，或存在多种会改变行为的解释；
- 拆出的功能全部完成仍无法兑现核心结果，或关键需求互相矛盾，需要重新决定“要解决什么问题”；
- 数据敏感度、产品形态、项目边界或风险前提被新证据推翻，原画像和流程档位不再适用。

按下面的顺序处理：

1. **指出差异**：对照用户原话、已确认决策和当前拆解，记录“原理解 → 冲突/反例 → 受影响的结果”。只暂停依赖该前提的工作，独立且仍在授权范围内的工作可继续。
2. **解决含义**：已有要求能唯一决定答案时，纠正 agent 的理解并说明依据，不重复请求确认；确有歧义、冲突或要改变已接受的目标时，向用户提出一个具体决策问题，包含候选、推荐和行为/范围代价。用户答复前，不替其选择核心目标或据此编造验收。
3. **同步权威记录**：记录结论和受影响的需求、A-ID、质量目标、架构及切片。涉及范围或行为变更时走 03-scope-and-nongoals.md 的变更协议，先更新目标合同/验收来源，再同步台账。仅澄清且含义不变时保留 ID；替换已承诺行为时保留旧记录和变更指针，新增验收 ID，不覆盖 delivered 的历史含义或把它退回未完成。
4. **重新判断影响**：更新画像、档位和路径；将受影响的阶段门禁及模块 `AGENTS.md` 标为待复核，记录恢复动作。保留无关代码与证据，旧测试通过不能证明变更后的行为成立。
5. **恢复拆解**：核心含义已解决、变更有记录后，回到阶段 1–4 中最早受影响的阶段；仍符合 LEAN 时更新一页合同。重新检查拆解能否兑现核心结果，再推进架构与实现。

局部问题按最小影响回退：目标明确但单条需求措辞不清回 01，验收断言不具体回 02，版本优先级不清回 03，阈值/实验缺失回 04。若处理时发现上面的根本前提问题，再升到 P0。

首次完成画像时，档位决定下一份文档；P0 回流后按上面的影响判断恢复：

- 档位为 **LEAN** 且 00-lean-path.md 的入口条件全部成立 → 进入 00-lean-path.md，把阶段 1–4 合并成一页项目合同；
- 其余情况（含 LEAN 但快路径入口不成立、不确定档位）→ 进入 01-requirements-and-goals.md 走完整路径。

完成画像后，把未知带到 04-constraints-quality-risks.md，把架构问题带到 05-architecture-design.md。画像本身不冻结服务数量、目录结构或数据库品牌。
