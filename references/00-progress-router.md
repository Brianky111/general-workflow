# 生命周期路由与阶段门禁

## 目标与边界

- 路由依据是用户请求、仓库事实和已确认决策，不替用户补造需求或架构；目录看起来完整不等于有行为证据。
- 用户指定阶段可以直接进入，但仍要按「全局门禁」的阻塞清单查前置条件。

## 第一次判断

先分清问方法还是动手：只问方法就直接回答，不建任何文件；动手才进写入路径。

动手前先找目标项目的 `docs/workflow/`。存在就用本 skill 绝对路径调状态脚本，`--root` 指向目标项目：

```powershell
python "<skill绝对路径>/scripts/workflow_status.py" --root "<目标项目绝对路径>" --json
```

退出码非零先修状态再推进。命令只读，写状态才加载 99-state-and-handoff.md。没有该目录就推导阶段，本轮结束前建立状态。

再收集最小上下文：

1. 用户要解决的问题、目标结果和期望动作；
2. 仓库处于空、脚手架、可运行代码还是生产流量哪一档；
3. 已确认的用户、入口、数据、外部依赖、环境和约束；
4. 最可能改变行为、范围、数据、安全或不可逆效果的未知。

### 画像按需加载

画像只产出档位、路径深度和要验证的风险，不给架构结论。脚本退出码 0 时 `tier` 和 `path` 已按枚举校验过，跳过画像直接进阶段选择——结论已在状态里，重算不多出信息，却可能把用户确认过的档位悄悄改掉，还把常驻从三份撑成四份。以下情况才加载 00-project-profile.md：

- 没有 `docs/workflow/` 的新项目；
- `tier` 或 `path` 缺失、打印成 `?`，或与本轮仓库事实冲突；
- 路由算法第 3 步的 P0 回流成立。

`tier` 为 HIGH-RISK 时另加一条：进入任何阶段前读 00-project-profile.md 的「HIGH-RISK 加深清单」，按当前阶段那一行补证据，只取表不重定档位。反例是接手 `tier: HIGH-RISK`、`stage: 8` 的项目：上面三条都不成立，跳过画像就把 08 那一行一起跳过，而阶段文档不再自己写高风险要求，没有第二处可读。

## 生命周期状态

| 状态 | 含义 | 主要退出证据 |
| --- | --- | --- |
| IDEA | 只有想法，目标未成合同 | 最小目标合同 |
| DEFINED | 用户、结果、场景、范围已明确 | 验收场景、非目标和变更边界 |
| ARCHITECTURE-READY | 边界、数据和关键机制有可重评决策 | ADR/图/表及架构验证计划 |
| BOOTSTRAPPED | 仓库、工具链和基础 CI 可运行 | 干净 clone 验证和 CI 记录 |
| SLICE-READY | 首条切片连接真实入口、结果和关键假设 | 切片地图与切片门禁 |
| BUILDING | 以行为为单位实现并保持绿色 | 真实入口测试与集成结果 |
| RELEASE-CANDIDATE | 范围已过必要测试、评审和构建 | 发布清单、产物和回滚证据 |
| OPERATING | 已发布，在观察指标、告警和结果 | 发布后观察记录 |
| PAUSED | 用户或外部条件要求暂停，证据保留 | 明确恢复条件 |
| CANCELLED | 用户决定不再交付当前范围 | 取消原因和遗留风险 |

## 路由算法

按以下顺序执行：

1. **提问还是动手**：见「第一次判断」。
2. **判断 Greenfield 边界**：接手旧系统、重构、迁移、故障恢复，或存在要兼容的旧 API、旧数据、线上用户、已有部署时，先说明版本边界，标为额外风险并请用户确认是否纳入。确认后 `compat_surface` 从 none 改成实际兼容面，约束带进阶段 4 和 5；主线阶段不变，09 补兼容与迁移证据，10 的回滚覆盖新旧共存。不确认就只做不触碰兼容面的部分，或停下来问；两种走法都不切到 archive/ 旧流程。
3. **复核画像与原始意图**：拆解暴露目标歧义、矛盾或前提失效时，先走 00-project-profile.md 的 P0 回流。档位按「画像按需加载」处理，不确定时选完整路径。
4. **寻找最早未满足门禁**：按下表选择最早会影响当前结果的阶段，而不是最早缺少的文档。
5. **只加载当前 reference**：按「全局门禁」做完该阶段；除非当前文档要求，不递归加载其余参考。
6. **保留未决事项**：按「全局门禁」的阻塞清单判断，清单外的记下来继续做，不打断用户。
7. **阶段可连续推进**：门禁已被现有证据满足就同一轮进下一阶段，不为形式“审批”停住。
8. **每轮结束给出状态**：按 SKILL.md 的「默认响应形状」报告。

| 有目标但没有可观察的用户行为 | 2 | 02-scenarios-and-acceptance.md |
| 需求过宽或没有版本边界 | 3 | 03-scope-and-nongoals.md |
| 性能、安全、合规、成本或恢复风险未知 | 4 | 04-constraints-quality-risks.md |
| 系统形态、模块边界、数据所有权或技术栈未决 | 5 | 05-architecture-design.md |
| 05 的机制清单中有“现在必须有”或“由风险触发” | 5 | 05a-mechanisms-and-contracts.md |
| 架构已选但仓库无法从零运行 | 6 | 06-scaffolding-and-ci.md |
| 没选出能验证价值和架构的最短路径 | 7 | 07-vertical-slice.md |
| 切片明确但行为尚未实现 | 8 | 08-implementation-tdd.md |
| 实现存在但跨边界、真实依赖或评审证据不足 | 9 | 09-testing-review-integration.md |
| 可交付但没有可追溯产物、监控或恢复方案 | 10 | 10-release-operations.md |

P0 回流优先于 LEAN；快路径合同有效时从阶段 5 继续，入口条件任一不成立就跳过该行。事实仍成立的行跳过；新证据使前提失效就重核受影响门禁，已有文档不代表通过。

切片过 09 后进 10 还是回 7 认领下一条，由 `delivery_target` 的终点决定：逐条上线走 10→11
再回 7；整批交付留在 7，直到 backlog 没有 remaining 再进 10。

## 全局门禁

每个阶段用同一组问题收口：SKILL.md「统一阶段规则」的四件事，再加一问——游标：状态文件的阶段、决策、未决事项和证据是否推进到本阶段的结论？

游标**每次通过阶段门禁时**都答，不是轮末答一次；连推多阶段就逐阶段落盘。规则见 99-state-and-handoff.md。

以下情况才算阻塞：

- 当前验收行为没有定义，或存在互相冲突的已确认要求；
- 数据所有权、一致性、安全边界、公共兼容或不可逆迁移尚未决定；
- 真实入口、必要外部依赖或构建环境无法运行；
- 必须的测试、迁移、备份、监控或回滚证据缺失；
- 风险实验失败且没有已接受的替代方案。

通常不阻塞：可选模板、未来抽象、非当前范围的优化；框架或目录命名偏好；没有触发条件的完整矩阵、额外评审或 100% 覆盖率。

## 路径深度与暂停

- **快路径（LEAN）**：减免清单只在 00-lean-path.md，进入任何阶段前按那一份执行。这里不抄第二份，抄本会漂：读旧拷贝的人会以为 06 的干净 clone 也能省。
- **完整路径（STANDARD）**：逐阶段推进，机制与契约按标记加载 05a，09 增加集成与合同证据。
- **加深路径（HIGH-RISK）**：加深清单只在 00-project-profile.md，走法见「画像按需加载」，同样不抄第二份。

档位只决定最低证据，不妨碍用户要求更严格的流程。升级触发见 00-lean-path.md；触发成立就切回完整路径，已有产出直接搬运，不作废。

需要用户决策时，用以下格式问一个具体问题：

~~~markdown
决策：<会改变的行为/范围/数据/安全/成本>
背景：<已知事实和候选方案>
推荐：<方案及理由>
代价：<接受什么、放弃什么>
不决策的后果：<会阻塞哪条路径>
~~~

不要把“请确认所有内容”当成问题，也不要在没有新信息时重问已明确的选择。

## 结束与回流

交付终点按 99-state-and-handoff.md 的“范围完成与任务结束”核验；仍欠发布工作就继续阶段 10。完成后：

1. closeout 简短、可复现、可追溯，内容见 SKILL.md「交付完成条件」，游标写回状态文件；
2. 实际发布后才进入 OPERATING 或 11-retrospective-evolution.md，否则保留当前生命周期；
3. 没有新的用户目标或运行证据时，不自动开启重构；
4. 拆解矛盾、需求变化或运行证据使前提失效时，按阶段选择表回流。

closeout 完成后停止当前循环。
