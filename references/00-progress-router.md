# 生命周期路由与阶段门禁

本文件路由当前阶段、下一动作和必要证据，不替用户补造需求或架构。

## 目标与边界

- 默认处理 Greenfield 项目：没有既有业务实现需要保持兼容，或用户明确要求从零重建。
- 先读本文件，再按当前阶段只加载一份 reference。Reference Map 是索引，不是要求一次性阅读的清单。
- 路由依据是用户请求、仓库事实和已确认决策；文件名、目录是否“看起来完整”不能替代行为证据。
- 用户明确指定阶段时可以直接进入该阶段，但仍要检查会导致返工、数据损失、安全漏洞或无法运行的实质性前置条件。
- 如果发现任务其实是接手旧系统、重构、迁移或线上故障恢复，先说明当前版本边界，除非用户确认扩展范围，否则不要偷偷切换成旧版流程。

## 第一次判断

先找目标项目的 `docs/workflow/`。存在就按 99-state-and-handoff.md 的命令，从本 skill 绝对路径调用脚本，以 `--root` 指定目标项目；退出码非零先修状态。否则推导阶段，本轮结束前建立状态。

再收集最小上下文：

1. 用户要解决的问题、目标结果和期望动作；
2. 当前仓库是否为空、只有脚手架、已有可运行代码，还是已有生产流量；
3. 已确认的用户、入口、数据、外部依赖、环境和约束；
4. 当前最可能改变行为、范围、数据、安全、兼容性、成本或不可逆效果的未知。

随后阅读 00-project-profile.md，形成项目画像。画像不是架构结论，而是决定流程深度和需要验证的风险。

## 生命周期状态

| 状态 | 含义 | 主要退出证据 |
| --- | --- | --- |
| IDEA | 只有想法或问题描述，目标尚未形成合同 | 最小目标合同 |
| DEFINED | 用户、结果、场景、范围已足够明确 | 验收场景、非目标和变更边界 |
| ARCHITECTURE-READY | 架构驱动、边界、数据和关键机制已有可重评决策 | ADR/图/表及架构验证计划 |
| BOOTSTRAPPED | 仓库、版本、工具链、配置和基础 CI 可运行 | 干净 clone 验证和 CI 记录 |
| SLICE-READY | 第一条切片连接真实入口、结果和关键假设 | 切片地图与切片门禁 |
| BUILDING | 正在以行为为单位实现并保持绿色 | 真实入口测试与集成结果 |
| RELEASE-CANDIDATE | 当前范围已通过必要测试、评审和构建 | 发布清单、产物和回滚证据 |
| OPERATING | 已发布，正在观察指标、告警和用户结果 | 发布后观察记录 |
| PAUSED | 用户或外部条件要求暂停，保留当前证据 | 明确恢复条件 |
| CANCELLED | 用户决定不再交付当前范围 | 取消原因和遗留风险 |

状态是工作判断，不要求为了每个状态创建额外文件。若项目已有 issue、ADR、README 或发布系统，优先复用它们作为权威来源。

## 路由算法

按以下顺序执行：

1. **先确定目标是否仍在范围内**：如果用户只是询问方法，回答方法，不创建项目文件；如果用户要求实现，才进入写入路径。
2. **判断 Greenfield 边界**：若存在需要兼容的旧 API、旧数据、线上用户或已有部署，标记为额外风险并请用户确认是否纳入。
3. **复核画像与原始意图**：拆解暴露目标歧义、矛盾或前提失效时，先走 00-project-profile.md 的 P0 回流；再选择 LEAN、STANDARD 或 HIGH-RISK。
4. **选择路径深度**：档位为 LEAN 且 00-lean-path.md 的入口条件全部成立时，走快路径，把 01–04 合并成一页项目合同；否则走完整路径。不确定时走完整路径。
5. **寻找最早未满足门禁**：按下表选择最早会影响当前结果的阶段，而不是最早缺少的文档。
6. **只加载当前 reference**：完成该阶段的目的、产出和退出门禁；除非当前文档明确要求，否则不递归加载全部参考。
7. **保留未决事项**：只有会改变行为、范围、数据含义、安全、兼容性、成本、所有权或不可逆效果的事项才暂停并向用户提问。
8. **阶段可连续推进**：若门禁已由现有证据满足，可以在同一轮进入下一阶段；不要为了形式上的“审批”停住。
9. **每轮结束给出状态**：写明状态、证据、剩余阻塞、下一动作和验证命令，并更新状态文件。

P0 回流优先于 LEAN。快路径用“一页项目合同”行替代 1–4；合同有效时从阶段 5 继续。完整路径忽略 LEAN 行。

跳过事实仍成立的行；新证据使前提失效时重新核验受影响门禁，已有文档不代表通过。

用户指定阶段时直接定位，检查实质性前置条件。

## 全局门禁

每个阶段都用同一组问题收口：

- 目的：减少了哪个不确定性，或交付了哪个可观察能力？
- 入口：哪些事实、权限、依赖和决策已经存在？
- 产出：哪些代码、配置、决策记录、测试或运行证据真正落地？
- 退出：什么命令、场景、日志、CI 记录、截图或发布记录能证明完成？
- 游标：状态文件的阶段、决策、未决事项和证据是否已推进到本阶段的结论？

最后一问在**每次通过阶段门禁时**回答，不是只在一轮对话结束时回答；一轮连推多个阶段时，每个阶段的结论都要落盘。状态文件的规则见 99-state-and-handoff.md。

以下情况才算阻塞：

- 当前验收行为没有定义，或存在互相冲突的已确认要求；
- 数据所有权、一致性、安全边界、公共兼容或不可逆迁移尚未决定；
- 真实入口、必要外部依赖或构建环境无法运行；
- 必须的测试、迁移、备份、监控或回滚证据缺失；
- 风险实验失败且没有已接受的替代方案。

以下情况通常不阻塞：

- 可选模板、未来抽象、非当前范围的优化；
- 个人偏好的框架或目录命名；
- 没有触发条件的完整矩阵、额外评审或追求 100% 覆盖率。

## 路径深度与暂停

- **快路径（LEAN）**：把 1–4 合并成 00-lean-path.md 的一页项目合同，05 只产出一页决策表，跳过 05a-mechanisms-and-contracts.md，除非鉴权、异步或对外契约中有任意一项是“现在必须有”。06 的干净 clone 验证和基础 CI 不能省。
- **完整路径（STANDARD）**：逐阶段推进，机制与契约按标记加载 05a，09 增加集成与合同证据。
- **加深路径（HIGH-RISK）**：在完整路径上显式列出风险实验、独立评审、迁移演练、容量证据和分批发布。

档位只决定最低证据，不限制用户主动要求更严格的流程。快路径的升级触发见 00-lean-path.md；触发成立时立即切回完整路径，已有产出直接搬运，不作废。

需要用户决策时，用以下格式提出一个具体问题：

~~~markdown
决策：<会改变的行为/范围/数据/安全/成本>
背景：<已知事实和候选方案>
推荐：<方案及理由>
代价：<接受什么、放弃什么>
不决策的后果：<会阻塞哪条路径>
~~~

不要把“请确认所有内容”作为问题，也不要在没有新信息时重复询问已经明确的选择。

## 结束与回流

按 99-state-and-handoff.md 的“范围完成与任务结束”检查交付终点；仍欠已要求的发布工作时继续阶段 10，完成后：

1. 记录版本/提交、关键证据、已知遗留风险和下一条切片，并把游标写回状态文件；
2. 实际发布后才进入 OPERATING 或 11-retrospective-evolution.md，否则保留当前生命周期；
3. 如果没有新的用户目标或运行证据，不自动开启重构；
4. 拆解矛盾、需求变化或运行证据使前提失效时，按阶段选择表回流。

全局 closeout 应简短、可复现、可追溯；完成后停止当前循环。
