# 条件深化：多存储、异步队列与数据同步

本文件仅在满足触发条件时按需加载，避免将分布式复杂性误套进单进程单库项目。

## 触发信号与退回条件

满足以下任一**当前需求明确包含或已确认存在**的信号时加载本文件并将约束写入 `docs/arch/dataflow.md` 与 `docs/arch/contracts.md`（“以后可能需要”“这样更稳健”不能成为引入异步/持久化/多版本机制的理由）：

- 系统包含 **`>= 2` 个有状态存储**（如关系库 + 搜索索引/缓存/对象存储）或 **`>= 2` 个独立部署单元**；
- 引入**消息队列、异步 Worker、定时批处理或跨服务事件总线**；
- 存在**有外部不可逆副作用的接口**（支付扣款、第三方 Webhook、发信/短信、云资源创建）；
- 支持**离线编辑或跨端增量同步**，或将缓存作为影响业务正确性的路径。

若核查发现仅为单进程单主库读写且当前无跨版本共存需要，立即退出本文件，保持单库本地事务与直接传播错误，不主动增设 Outbox、重试队列表或 Expand-Contract 过渡层。

## 单一真相源与禁裸双写

基于 Kleppmann《数据密集型应用系统设计》的核心纪律：

1. **严禁“先写 DB 再裸发消息 / 调外部 API”**：数据库提交成功而随后发 MQ 失败（或相反）必然撕裂状态。跨存储/外部触发必须使用**事务型 Outbox 表**（与业务状态同库同事务落盘，由独立中继消费并标记已派发），或由单一不变事件日志衍生所有状态。
2. **派生视图必须具备确定性重建路径**：搜索索引（ES/Meilisearch）、计数汇总、物化缓存或读模型都不是真相源。每张派生视图必须在 `dataflow.md` 写明两件事：1) 落后真相源时的可见语义；2) 从真相源**全量回放或增量修复的幂等重建脚本**。

## 幂等键、租约令牌与乱序容错

1. **全链路业务幂等键**：所有可能触发重试的写接口、Webhook 接收端与异步任务消费者，必须在契约层强制要求调用方或上游提供唯一 `idempotency_key`（搭配防重放唯一索引及参数摘要校验——同 key 不同入参显式拒错）。
2. **租约与单调 Fencing Token**：分布式锁、主从切换或定时 Worker 抢占任务时，禁止只靠 TTL 过期“假定”旧执行者已死；持久化写入端必须核对单调递增的 `fencing_token` 或乐观锁版本号，拒绝迟到旧写入覆盖新状态。
3. **显式声明一致性窗口**：在 `dataflow.md` 标明哪些读路径要求“读己之写（Read-your-writes）”（例如创建后立刻跳详情页，直读真相源或带写版本令牌），哪些报表可接受明确上限内的最终一致。

## 在途兼容演进（Expand-Contract）

多进程或多版本客户端并存时，Schema 与队列 Payload 演进禁止“一次性破坏性切换”：

1. **Expand**：先兼容新旧结构（新字段可空、消费者同时读旧新版本字段）；
2. **Migrate / Dual-Read**：发布兼容读取与迁移写入；
3. **Contract**：确认在途旧消息/旧节点清零后再删除旧字段与兼容分支。

## 分布式深化门禁

回填 `01b-dataflow-and-contracts.md` 前核对：

1. 每条跨存储或外部副作用链路均已消灭裸双写（采用 Outbox 或明确幂等补偿），且派生视图有可重跑重建路径；
2. 每个异步消费者与外部回调契约均定义了 `idempotency_key`、死信/最大重试上限与 Fencing/版本校验；
3. 数据演进方案满足多版本在途兼容，失败模式表已逐行补齐对应验证钩子。
