# 垂直切片

垂直切片是一条最短、真实、可部署的路径：从真实入口走到真实结果。本文件同时服务第一条切片和其后的每一条——从零到交付完整需求要走很多条，它们用同一套地图和同一组门禁，只是选择时的权重不同。

## 目的与入口

目的：

- 让用户或调用系统看到一个完整结果；
- 第一条切片额外承担：验证入口、组合根、数据、外部依赖和观测是否真的接通；
- 用真实路径发现边界错误，而不是在文档里假设一切可行。

入口：

- 06-scaffolding-and-ci.md 已通过 Bootstrap Ready（仅第一条切片需要检查；后续切片沿用同一骨架）；
- A-ID 场景和 R-ID 需求可追踪（快路径的等价物见 00-lean-path.md 的对接表）；
- 第一条切片还需要 05 阶段待验证的架构假设和风险证据；
- 后续切片还需要状态文件中未交付的 A-ID 清单，见 99-state-and-handoff.md。

## 选择标准

为候选场景按以下问题排序：

| 维度 | 问题 |
| --- | --- |
| 用户价值 | 完成后是否得到核心结果，而不是只看到内部状态？ |
| 风险信息量 | 是否触及最高价值的架构/外部依赖/数据假设？ |
| 端到端完整性 | 是否能从真实入口走到持久化或真实副作用再回到可观察结果？ |
| 可控性 | 是否能在当前环境、时间和权限内部署、观察和回滚？ |
| 后续复用 | 是否建立后续切片会复用的稳定边界，而不是一次性旁路？ |

优先选“最小但完整”，不要选只验证 UI 的假切片、只验证数据库的脚本或一次性 mock 流程。

### 首条与后续切片的权重差别

同一张表，权重不同。判断“这是第几条”看的是架构假设是否已被真实运行证据验证过，不是看切片序号：

| 维度 | 第一条切片 | 后续切片 |
| --- | --- | --- |
| 风险信息量 | **最高权重**：必须触及一个未验证的架构假设 | 降为触发项：只有引入新依赖、新运行单元或新数据边界时才要求 |
| 端到端完整性 | 必须首次打通入口→持久化→可观察结果的整条路径 | 复用已打通的路径；新增的只是这条切片自己的分支 |
| 后续复用 | 建立后续切片要复用的稳定边界 | 复用既有边界；若被迫绕开，说明边界有问题，回到 05；重定边界后的改动超出本切片 write_scope 时走 00-refactor-path.md |
| 选择依据 | 价值 × 风险信息量 | **优先关闭未交付的 Must**：从状态文件的 remaining 中挑，兼顾依赖顺序 |
| 架构假设 | 必须有 H-ID 及通过条件 | 通常为 none；填 none 是合法结论，不要为了填表编一个假设 |

后续切片不因为“少了架构假设”就降低门禁：真实入口、可观察结果、失败路径、证据和回滚要求完全一致。

## 切片地图

切片地图不是另一个文件，而是 `docs/workflow/slices/S-0N.md` 里的一节。该文件的头部字段
（owner、claimed、stage、write_scope、architecture_hypothesis）和 `## Acceptance` 表由
99-state-and-handoff.md 定义并被状态脚本校验；本阶段负责补上下面这一节：

~~~markdown
## Slice map
- user_outcome: <对应目标>
- requirements: R-01, ...      # 快路径用 must 条目，见 00-lean-path.md 的对接表
- acceptance: A-01, A-02, ...  # 与本文件 ## Acceptance 表的 A-ID 一致
- real_entrypoint: <HTTP/CLI/event/scheduled>
- path:
  1. 输入与身份
  2. 校验
  3. 应用用例
  4. 领域规则/状态转换
  5. 数据库或外部依赖
  6. 结果/事件/可观察副作用
- failure_paths: <关键失败和可见语义>
- data_changes: <迁移、索引、所有权>
- observability: <日志、指标、追踪、告警>
- test_evidence: <单元/集成/合同/E2E>
- deploy_and_rollback: <如何进入 staging、如何撤回>
- out_of_scope: <明确不做>
~~~

头部的 `architecture_hypothesis` 填 05-architecture-design.md 架构验证计划表里的 H-ID，
或 `none`；不在本阶段现编一个假设。

路径中的每一步都要指向真实代码和真实注册点。测试替身可以隔离不可控第三方，但不能把核心业务路径换成测试专属实现。

## 模块级 AGENTS.md

认领切片后、修改代码前，识别所涉模块并读取目标路径适用的根与嵌套指令。新建或更新的指令也要显式读取。一个切片可以跨多个模块，一个模块也会被多条切片修改。

具有独立职责、特殊约束或验证方式的模块，按需建立简短的 `AGENTS.md`；没有额外规则的目录沿用上级指令，不为每个目录或 A-ID 生成文件。首次写入依据已确认的阶段 5 决策；未验证假设链接 ADR，不写成既成事实。

模块指引只保存：职责和非职责、公开入口、数据所有权与依赖边界、易误用约束、实际验证命令和权威文档链接。需求/BDD 场景、ADR、接口契约保留在各自权威位置；当前任务、owner 和证据保留在切片状态中。规则没有变化时无需改文件。

示例结构（替换占位后使用）：

~~~markdown
# <模块名称>
- 职责与边界：<负责什么，不负责什么；指向架构决策>
- 公开入口：<真实路由 / 用例 / 消费者及注册位置>
- 数据与依赖：<拥有的数据、允许调用的接口、禁止的跨模块访问>
- 验收来源：<权威 BDD 场景 / A-ID 表的路径和章节>
- 验证入口：<测试文件或证据映射；实际命令及运行目录、必要环境>
- 特殊检查：<本模块必须检查的失败、权限、状态或副作用边界>
~~~

模块指引维护沿用本切片的写入范围；多个切片共同修改时先协调归属。跨模块验收沿用 09-testing-review-integration.md 的证据映射，不在各模块重复定义完整场景。指令不自行扩大需求、增加审批或改变所有权；重要约束仍由真实测试和必要的静态检查验证。

## 认领规则

认领就发生在本阶段：选定切片、建立切片文件、把 A-ID 从未认领转到自己名下。第二个人加入的第一分钟也走这条路——跑一次状态脚本，看见哪些 A-ID 未认领，认领一条，开工。切片文件和 backlog 的格式由 99-state-and-handoff.md 定义，下面七条规定谁能写、能写多少、怎么退出。

1. **认领即在自己的切片文件里写上 owner 和 claimed**，同时把 backlog 中对应 A-ID 的 slice 列指向该切片。认领会修改共享 backlog；开始工作前同步认领记录并重跑校验，不能把文件分片当作跨分支的原子锁。
2. **不要抢一个 owner 有新鲜证据的切片**（近期提交、CI 运行、刚更新的 evidence）。接手先与该 owner 或用户确认。
3. **在途切片必须有 owner、有效 claimed 日期和 write_scope。** 路径是项目内的真实文件/目录，不支持 glob；`.` 表示整个项目，只在没有其他在途切片时可用。脚本解析 `.`、`..`、已有链接及 Windows 大小写后检查重叠；重叠先调整边界或排序，不同时开工。
4. **一次一条。** 同一 owner（忽略大小写）只能持有一条**在途**切片。在途 = 有 in-slice 行，或已写上 owner 但还没有任何 delivered 行——认领发生在验收行写下之前，空切片一样占住 write_scope。全部行 delivered 后该切片释放路径，可以认领下一条。唯一的例外是功能切片因自己的重构停下来：在它头部写 `- waiting_on: R-0N`，这一对可以同时在途、write_scope 可以重叠，重构收口后清掉这一行再继续；没写就按两条在途切片拒绝。重构切片本身怎么认领和收口，见 00-refactor-path.md。
5. 接手一条 stale 切片（owner 已久无证据）时，在该切片文件里记录交接原因和日期。
6. **归还与改判。** 不做这条切片了，三件事要一起做：把未完成的 A-ID 行从切片文件删掉；backlog 对应格改回 `-`，或改成 `deferred`/`dropped` 并指向变更记录；把切片文件的 `owner` 和 `claimed` 清空（各填 `-`），一条 delivered 都没有时也可以直接删掉整个切片文件。原因写进 Blockers。漏掉第三件事会被自己的归还锁住：按第 4 条，有 owner 而没有任何 delivered 行就算在途，只删验收行留下的是一条永远在途的空切片，同一个 owner 认领下一条时会撞上 `owner holds two live slices`。归还不是“删行凑完成”——A-ID 仍在来源和 backlog 里，完成度是变远不是变近。已 delivered 的行不参与归还，它们的证据留在原切片文件里。
7. **范围中途变化。** 要动 write_scope 之外的路径时就地修订并重跑脚本。与在途切片重叠时由两个 owner 约定边界：一方收窄，或把这处改动交给该路径的 owner，结论写进 Blockers。

## 切片拆解顺序

1. 先确认真实入口和最小输入/身份；
2. 画出应用用例、领域规则和数据/外部端口；
3. 设计成功与一个最有信息量的失败路径；
4. 加入必要的迁移、配置、日志和指标；
5. 为每个行为预留 TDD 测试位置；
6. 在本地和 CI 运行，必要时部署到 staging；
7. 对照 H-ID 的预期证据判断架构假设是否成立。

若切片无法在当前环境中运行，先回到 05 架构或 06 脚手架解决真实阻塞，不要用旁路脚本伪造完成。

## Slice Ready 门禁

进入 08-implementation-tdd.md 前，必须明确：

- 一个可观察的用户/系统结果及其 A-ID；
- 真实入口、组合根和生产依赖；
- 最小成功路径和至少一个风险相关失败路径；
- 数据写入、状态、不变量和副作用；
- 需要验证的架构假设及通过条件；
- 预期单元、集成、合同或 E2E 证据；
- 配置、迁移、观测、部署和回滚边界；
- 已读取所涉模块的适用指令，必要的局部指引已补齐且与权威决策一致；
- 切片文件已按本文件 `## 认领规则` 认领：owner、claimed、write_scope 和 `## Slice map` 已填，状态脚本退出码为零；
- 当前明确不做的相邻功能。

## 何时更换切片

如果候选切片暴露出不可接受的架构假设失败，记录结果并回到 04/05；不要继续堆代码证明错误方向。若只是实现细节困难且不改变边界，保持切片范围，进入 TDD 循环。

## 交付完成的判定

统一使用 99-state-and-handoff.md 的“范围完成与任务结束”规则。本文件 `## 认领规则` 的认领只把 A-ID 从 remaining 转为 in-slice，不代表完成；状态脚本的范围结论还必须结合已授权交付终点才能决定是否 closeout。

remaining 非空但用户决定收尾时，把剩余 A-ID 显式改判为延后或非目标，走 03-scope-and-nongoals.md 的变更协议，不要让它们无声消失。
