# 第一条垂直切片

第一条垂直切片不是把最多功能塞进首个迭代，而是选择一条最短、真实、可部署的路径，同时验证用户价值和一个关键架构假设。它连接需求、架构、代码、测试、CI 和发布。

## 目的与入口

目的：

- 让用户或调用系统看到一个完整结果；
- 尽早验证入口、组合根、数据、外部依赖和观测是否真的接通；
- 用真实路径发现架构边界错误，而不是在文档里假设一切可行。

入口：

- 06-scaffolding-and-ci.md 已通过 Bootstrap Ready；
- A-ID 场景和 R-ID 需求可追踪；
- 05 阶段已有待验证的架构假设和风险证据。

## 选择标准

为候选场景按以下问题排序：

| 维度 | 问题 |
| --- | --- |
| 用户价值 | 完成后是否得到核心结果，而不是只看到内部状态？ |
| 风险信息量 | 是否触及最高价值的架构/外部依赖/数据假设？ |
| 端到端完整性 | 是否能从真实入口走到持久化或真实副作用再回到可观察结果？ |
| 可控性 | 是否能在当前环境、时间和权限内部署、观察和回滚？ |
| 后续复用 | 是否建立后续切片会复用的稳定边界，而不是一次性旁路？ |

优先选“最小但完整”，不要选只验证 UI 的假切片、只验证数据库的脚本或一次性 mock 流程。

## 切片地图

~~~markdown
# Slice S-01: <名称>
- user_outcome: <对应目标>
- requirements: R-01, ...
- acceptance: A-01, A-02, ...
- architecture_hypothesis: H-01 <要验证的假设>
- real_entrypoint: <HTTP/CLI/event/scheduled>
- path:
  1. input and identity
  2. validation
  3. application use case
  4. domain rule/state transition
  5. database or external dependency
  6. result/event/observable side effect
- failure_paths: <关键失败和可见语义>
- data_changes: <迁移、索引、所有权>
- observability: <日志、指标、追踪、告警>
- test_evidence: <单元/集成/合同/E2E>
- deploy_and_rollback: <如何进入 staging、如何撤回>
- out_of_scope: <明确不做>
~~~

路径中的每一步都要指向真实代码和真实注册点。测试替身可以隔离不可控第三方，但不能把核心业务路径换成测试专属实现。

## 切片拆解顺序

1. 先确认真实入口和最小输入/身份；
2. 画出应用用例、领域规则和数据/外部端口；
3. 设计成功与一个最有信息量的失败路径；
4. 加入必要的迁移、配置、日志和指标；
5. 为每个行为预留 TDD 测试位置；
6. 在本地和 CI 运行，必要时部署到 staging；
7. 对照 H-ID 的预期证据判断架构假设是否成立。

若切片无法在当前环境中运行，先回到 05 架构或 06 脚手架解决真实阻塞，不要用旁路脚本伪造完成。

## Slice Ready 门禁

进入 08-implementation-tdd.md 前，必须明确：

- 一个可观察的用户/系统结果及其 A-ID；
- 真实入口、组合根和生产依赖；
- 最小成功路径和至少一个风险相关失败路径；
- 数据写入、状态、不变量和副作用；
- 需要验证的架构假设及通过条件；
- 预期单元、集成、合同或 E2E 证据；
- 配置、迁移、观测、部署和回滚边界；
- 当前明确不做的相邻功能。

## 何时更换切片

如果第一条候选切片暴露出不可接受的架构假设失败，记录结果并回到 04/05；不要继续堆代码证明错误方向。若只是实现细节困难且不改变边界，保持切片范围，进入 TDD 循环。
