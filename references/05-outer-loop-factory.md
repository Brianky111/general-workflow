# 外循环成熟度与自动化工厂

当代码库本身和验证通道已经足够强硬时，Engineer 的杠杆才从“陪着一个 Agent 写代码”跃迁到“让外循环自动化持续发现问题、修复问题并在可控范围内合入”。顺序反过来就是灾难。

## 先内循环，再外循环

土豆姐在演讲里反复强调的一条铁律：**如果单次内循环（改代码 → 护栏检查 → 跑真实应用交产物）还会批量产垃圾，那把外循环放大成百上千个并行 Agent，只会更快地堆出一堆要人熬夜擦屁股的 PR，同时烧光算力与审查精力。**

在升入外循环之前，先问一个实事求是的问题：在当前的确定性护栏和 `verify_cli` 之下，一个中等能力模型在不被人工手把手提示的情况下，一次做对并交出合格产物的概率是不是已经很稳？如果不是，继续回到 `02` 和 `04` 补护栏、除草，不要急着开自动工厂。

## 成熟度阶梯（L0–L3）

本节是本工作流中**L0–L3 成熟度阶梯定义、升级前提与自动化边界的唯一权威**，其他文档（包括 `00-router.md`）只引用名称，不重抄下表。

| 层级 | 核心定义与自动化边界 | 升级前提与门禁 | 人的主要角色 |
| --- | --- | --- | --- |
| `L0` | **L0 低信任：尚未建成确定性护栏，禁止并行多 Agent 与自动合入** | 刚建项或刚接手旧仓，逃生舱尚未清零、边界规则或验证 CLI 尚缺 | 补基线检查、锁棘轮、建立首批核心护栏 |
| `L1` | **L1 产物审查内循环：确定性检查全绿且核心功能具备 Feature Map 与行为产物，人工审产物不逐行审 diff** | `check_command` 稳定通过，`.guardrails/feature-map.md` 与 `verification.md` 覆盖全部 `core` 功能 | 审录屏、截图、状态图与产物证据；每次纠错按 `04` 下沉 |
| `L2` | **L2 发版探索外循环：逃生舱清零后，发版或合入后自动启动探索 Agent 模拟真实用户 Fuzz 并提附带录屏的修复 PR** | 满足 `L1` 全部条件，且 `escape_hatches.max_allowed == 0`（旧债清零）与关键边界已做深度验证 | 验收探索 Agent 发现的新问题与附带录屏的修复 PR，继续补充护栏 |
| `L3` | **L3 高信任自动合入：验证必须锚定当前 HEAD，低风险产品修复按规则自动合入，不可逆边界仍保留人工门禁** | 长期低回退率、零逃生舱、`require_fresh_head: true` 且 `repo_guard.py --check-head --run-check` 进 CI 强制卡死 | 园丁与指标守门人：管意图、不可逆审批与护栏演化，不再逐个批日常修复 |

状态变更必须修改 `.guardrails/config.json` 中的 `trust_level`，并真实跑通 `repo_guard.py` 校验（例如 `L2`/`L3` 带着非零 `max_allowed`，或 `L3` 未开启 `require_fresh_head`，都会被脚本直接拒绝）。

### 发版后探索性测试（Release Fuzzing）做法

进入 `L2` 后，每次切新版本或合入重要改动，触发一个外循环作业：

1. 给探索 Agent 注入 `.guardrails/feature-map.md`（或 `verify_skill` 下的 `features/*.md`）与 `verify_cli` 入口；
2. 让它像真实用户一样全路径点击、随机跳转、组合边界输入（可叠加 UI PBT）；
3. 发现异常时必须交出复现步骤、录屏/截图以及证伪对比（修前必现、修后消失）；
4. 提修复 PR 并附产物——`L2` 由人审产物后合并，`L3` 在全部护栏与 `--check-head` 绿灯后按规则合入。
5. 随版本演进定期运行 `vendor/pstack/skills/maintain-verification-skill/SKILL.md` 与 `vendor/pstack/skills/maintain-formal-verification-skill/SKILL.md`，防止功能地图与形式化模型因合入漂移成假绿灯。

## 不可逆边界的永久人工门禁

即使仓库已经稳定在 `L3` 并且日常产品修复实现了自动合入，以下五类改动**永远保留人工确认门禁**，不得交给自动合入规则放行：

1. 破坏性数据库迁移、删表删字段或不可逆历史数据重写；
2. 资金流转、计费规则、额度与账本核心逻辑变更；
3. 认证、授权放宽、多租户隔离边界调整或秘密管理改动；
4. 破坏既有对外公共 API / 事件契约且无兼容窗口的变更；
5. 降低或放宽既有安全规则、提高 `escape_hatches.max_allowed` 或跳过 `check_head`。

## 真实质量指标（不只看 PR 数量）

Grok Bot 团队用 PR 数量证明护栏撑得住吞吐，但真正决定方向对不对的不是 PR 数量，而是下面两组指标：

- **PR 回退率（Revert Rate）**：注意回退率不等于零 bug 率，它衡量的是一段时间后才发现合错并回滚的比例。每次发生 revert，**不能只把代码回退了事**，必须顺着 `04-correction-and-gardening.md`（及 `vendor/pstack/skills/correct/SKILL.md`）做历史错误聚类与证伪回放：这次漏洞为什么穿过了护栏，缺的是哪个 API 约束、哪条原生 Lint 还是哪项验证？
- **用户可感的核心 KPI**：启动耗时、输入响应延迟、关键路径打开与切换速度、崩溃与错误率。如果 PR 数量暴涨但核心性能或体验变慢，说明外循环正在把系统推向退化，必须立刻降级回 `L1` 治理结构与护栏。

## 外循环门禁

启用或维持 `L2`/`L3` 外循环运行前，确认：

1. 内循环检查与全部 `core` 功能行为产物已稳定，且 `escape_hatches.max_allowed` 已降至 `0`；
2. 若配置为 `L3`，`require_fresh_head` 已开启且合并前必须通过 `repo_guard.py --check-head --run-check`；
3. 不可逆边界清单（来自 `01-intent-and-invariants.md`）已在 CI/分支保护规则中设为人工必审；
4. 已记录回退率或用户可感核心指标的观察基线，每次回退都有下沉为新护栏的复盘动作。
