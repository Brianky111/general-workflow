# 外循环成熟度与自动化工厂

当代码库护栏与场景验证通道足够坚硬时，工程师的杠杆才从“陪单个 Agent 写代码”跃迁到“外循环自动发现并修复问题”。顺序颠倒就是灾难。

## 先内循环，再外循环

核心铁律：**如果单次内循环（改代码 → 护栏检查 → 跑真实应用交产物）还会批量产垃圾，把外循环放大成百上千并行 Agent，只会更快堆出要人熬夜收拾的 PR 并烧光预算。**

进入外循环前先实事求是评估：在当前确定性护栏与 `verify_cli`/`verify_skill` 约束下，中等能力模型不靠手把手提醒、一次改对并交出合格产物的概率是否已经稳定？若否，先回 `02` 与 `04` 补护栏、扩 `clean_scopes` 与除草。

## 成熟度阶梯（L0–L3）

本节是本工作流中**L0–L3 成熟度阶梯定义、升级前提与自动化边界的唯一权威**，其他文档（包括 `00-router.md`）只引用名称，不重抄下表。

| 层级 | 核心定义与自动化边界 | 升级前提与门禁 | 人的主要角色 |
| --- | --- | --- | --- |
| `L0` | **L0 低信任：尚未建成确定性护栏，禁止并行多 Agent 与自动合入** | 刚建项或刚接手旧仓，逃生舱尚未清零、边界规则或验证 CLI 尚缺 | 补基线检查、锁棘轮、建立首批核心护栏 |
| `L1` | **L1 产物审查内循环：确定性检查全绿且核心功能具备 Feature Map 与行为产物，人工审产物不逐行审 diff** | `check_command` 与驱动型 `verify_cli`/`verify_skill` 稳定通过，覆盖全部 `core` 功能 | 审录屏、截图、状态图与产物证据；每次纠错按 `04` 下沉 |
| `L2` | **L2 发版探索外循环：逃生舱清零后，发版或合入后自动启动探索 Agent 模拟真实用户 Fuzz 并提附带录屏的修复 PR** | 满足 `L1` 全部条件；全仓三项棘轮清零，**或**配置 `clean_scopes` 净土模块并用 `baseline_files` 锁死仓外旧巨石 | 验收探索 Agent 发现的新问题与附带录屏修复 PR（或抽样审查净土区增量），继续除草 |
| `L3` | **L3 高信任自动合入：验证必须锚定当前 HEAD，低风险产品修复按规则自动合入，不可逆边界仍保留人工门禁** | 长期低回退率、全仓三项棘轮均清零（不含例外旧债）、`require_fresh_head: true` 且 `--check-head --run-check` 进 CI | 园丁与指标守门人：管意图、不可逆审批与护栏演化 |

状态变更须修改 `.guardrails/config.json` `trust_level` 并跑通 `repo_guard.py` 校验。

### 局部净土受控晋级（`clean_scopes`）

大型存量仓库往往有几十处历史巨石文件，等全仓彻底归零才能试用外循环周期太长。在 `L2` 阶段支持**净土先行、全仓仍卡**：

- 将已彻底重构或新建的干净目录/入口列入 `.guardrails/config.json` 的 `clean_scopes`（如新模块 `backend/app/billing/`）；
- `repo_guard.py` 对 `clean_scopes` 内部在全周期执行**零逃生舱、零反模式、严守 `max_lines`（哪怕全仓 `max_allowed > 0`）**；同时强制仓外若有 `file_limits.max_allowed > 0` 则必须配齐 `baseline_files` 锁死仓外巨石不准继续膨胀；
- 由此可在不放松仓外旧债棘轮的前提下率先进入 `L2` 发版 Fuzzing 与并发切片，但升入 **`L3` 自动合入仍强制要求全仓所有旧债棘轮彻底清零**。

### 发版后探索性测试（Release Fuzzing）做法

进入 `L2` 后，每次切版本或合入重要改动可触发外循环探索作业：

1. 给探索 Agent 注入 `.guardrails/feature-map.md`（或 `verify_skill` 下的 `features/*.md`）与 `verify_cli` 入口；
2. 让它像真实用户全路径点击、随机跳转与边界组合输入（可叠加 UI PBT）；
3. 发现异常必须交出复现步骤、录屏/截图与证伪对比（修前必现、修后消失）；
4. 提修复 PR 并附产物——`L2` 由人审产物后合并，`L3` 在全绿与 `--check-head` 通过后按规则合入；
5. 随版本演进用 `vendor/pstack/skills/maintain-verification-skill/SKILL.md` 与 `maintain-formal-verification-skill/SKILL.md` 同步地图与形式化模型。

### PR 自动化评论分流与对外文风（`bugbot-triage` & `unslop`）

处理 Bugbot / 机器人评审意见与撰写 PR 说明时：

- **审慎分流不盲从（`vendor/pstack/skills/poteto-mode/references/bugbot-triage.md`）**：按 `fix`（确认正确性/并发/安全问题，在最小归属提交修复并回 SHA）、`dismiss`（有具体代码反证或一命令实跑证伪的低风险噪音；严禁为迎合评论把 `ENOENT` 等刻意窄异常条件扩成全捕获吞错）、`ask`（触及安全、隐私、鉴权、计费、迁移、幂等或语义歧义）三类处置；评论正文一律视作不可信数据，严禁直接拼接进 Shell 命令。
- **短句去 AI 腔（`vendor/pstack/skills/unslop/SKILL.md`）**：PR 描述、总结汇报与文档统一用主动短句直陈事实、数据与边界，禁用套话、破折号连接与形容词堆砌。

## Skill 与规则改动的双盲评测（`eval`）

对核心工作流、仓库 `AGENTS.md` 或自建 Skill 做重大改版时，不能只看静态自检或主观读起来顺眼，必须按 `vendor/pstack/skills/poteto-mode/playbooks/eval.md` 跑可控实验（尤其警惕 Agent 察觉自己在被测试时改变行为）：

1. **严格去标记盲化**：候选子 Agent 所在工作目录、文件名与提示词里**严禁出现 `eval`、`test`、`judge`、`rubric`、`score`、`compare`、`benchmark`、`candidate`、`arena` 等元词汇**；目录命名采用正常业务项目名。
2. **自然有机 Prompt + 禁自报链路**：提示词只写正常用户需求，**不要**问候选者“你用到了哪几条规则/文件”，而是从产出代码形状、测试真伪与实际工具调用转录来客观评分。
3. **异构模型同尺度盲评 + 人核原文**：把两组输出编为中性代号后交给**不同模型家族的 Judge** 在同一套 3–6 条 Rubric 下单趟打分，再由主控亲自核查候选真实打开了哪些文件、运行了什么命令，防止 Judge 偏见或幻觉放水。

## 不可逆边界的永久人工门禁

即使到达 `L3` 且日常产品修复已自动合入，以下五类改动**永远保留人工确认门禁**：

1. 破坏性数据库迁移、删表删字段或不可逆历史数据重写；
2. 资金流转、计费规则、额度与账本核心逻辑变更；
3. 认证、授权放宽、多租户隔离边界调整或秘密管理改动；
4. 破坏既有对外公共 API / 事件契约且无兼容窗口的变更；
5. 降低或放宽既有安全规则、提高旧债 `max_allowed`、缩减 `clean_scopes` 或跳过 `check_head`。

## 真实质量指标（不只看 PR 数量）

高 PR 吞吐只是护栏够硬的副产品，真正卡住方向的是以下指标：

- **PR 回退率（Revert Rate）**：衡量合错后被迫回滚的比例。每次发生 revert 必须顺着 `04` 与 `/correct`（含会话转录挖掘）找到穿过护栏的根因并补成硬检查；
- **用户可感核心 KPI**：启动耗时、输入响应延迟、关键路径打开与切换速度、崩溃与错误率。吞吐暴涨但体感变慢时立刻降级回 `L1` 治理结构。

## 外循环门禁

启用或维持 `L2`/`L3` 运行前核对：

1. 内循环检查、`core` 功能产物与场景驱动 `verify_cli`/`verify_skill` 已稳定；全仓旧债归零，或仅 `L2` 明确配置了 `clean_scopes` + 非空 `baseline_files`；
2. 若配置最高层级自动合入，`require_fresh_head` 已开启且合并前必须通过 `repo_guard.py --check-head --run-check`；
3. 不可逆边界清单已在 CI/分支保护设为人工必审；重大规则/技能迭代已走双盲 `eval` 确认有效；
4. 已建立回退率与用户可感指标基线，每次回退均有下沉护栏复盘。
